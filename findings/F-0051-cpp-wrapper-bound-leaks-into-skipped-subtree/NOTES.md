# F-0051 — `corelib-cpp` keeps a wrapper's element-index bound armed **inside a skipped subtree**

**Found 2026-08-02** while resolving whether `cpp` belonged on F-0047's impl list. It does not:
its mechanism is different, its owner is different, and it needs its own issue.

## The question this answers

The Go steering engine's cluster 15 minimized to F-0047's construct but with **cpp in the
rejecting camp**, where F-0047's own vectors put it in the correct one. The obvious move was to
add cpp to [generator#272](https://github.com/sofa-buffers/generator/issues/272). That would
have been wrong.

## The two mechanisms, separated by one control

| vector | `c`, cpp-c-cpp, go, py×2, ts | **cpp** | csharp, dart, java, rust×2, zig |
|---|---|---|---|
| `ctl_child_in_range` — mistyped element, child id **0** | accept → **empty** (skipped) | accept → **empty** ✅ | accept → `string_array[0]="A"` (**entered**) |
| `r1_mistyped_elem_child_overindex` — same, child id **5** | accept → empty | **`R invalid_msg`** ❌ | `R invalid_msg` |

The control is the whole argument. With an in-range child, **cpp skips the mistyped element
correctly** — it produces the empty message, exactly like the six conformant impls, while the
six F-0047 impls enter and bind the child. So cpp does *not* enter the subtree.

Then it cannot be rejecting `r1` because it "found an over-index element": it never treated the
child as an element at all. What it does instead is keep the **wrapper's schema `count` bound
armed while skipping**, so a child id ≥ 5 anywhere inside the skipped subtree trips the §7.1
over-index reject.

Same symptom as F-0047, opposite mechanism: **F-0047 is enter-and-bind; this is
skip-but-still-enforce.**

## It is not specific to mistyped elements

`r2_unknown_seq_child_overindex` replaces the §7.3-mistyped element with an **unknown field id**
(50) — a different reason to skip, same subtree shape — and cpp rejects identically. So the
bound leaks into *any* skipped subtree inside the wrapper, not just a mistyped element's.

`ctl_overindex_in_struct_scope` puts the same over-index child inside `nested` (a struct, no
`count`): **all 13 agree**. So it is the wrapper's bound and nothing else.

## Spec basis

MESSAGE_SPEC **§7.3** — a field whose wire type contradicts the schema is skipped — and **§5.2**
for an unknown id. corelib-cpp's own header states the rule it is meant to follow, in
`StringSeq`'s documentation of `elemWire`/`elemFix` (`include/sofab/sofab.hpp:2986`):

> The §5.1/§7 over-index reject applies only to an element whose header agrees with this — one
> that contradicts it **is not this array's element at all** and is skipped like an unknown id,
> **bound or no bound**.

"Bound or no bound" is exactly the property that fails here — one level down. The element itself
is correctly exempted; its *children* are not.

## Attribution — `corelib-cpp`, not codegen

- The generated code hands the corelib everything it needs and nothing it shouldn't:
  `sofab::StringSeq _r0{string_array, 5, 64}; is.read(_r0);`. The `count` is passed **in**, and
  the element type is published to the stream as `StringSeq::elemWire`/`elemFix`, picked up at
  `sofab.hpp:2498`. Enforcement is entirely the corelib's.
- The sibling profile settles it: **`cpp-c-cpp` is correct**. It is generated by the same C++
  backend and differs only in which corelib it links (the C one, via
  `FixedStringSeq`/`readSequence`). A codegen defect would not split the two C++ profiles along
  the corelib boundary — that is the F-0013 / F-0050 signature.

## Where it likely sits

`IStreamImpl`'s element gate (`include/sofab/sofab.hpp:1843`) runs the §7.3 type test only for
ids **already at or past the bound**:

```cpp
if (elemBound_ >= 0 && elemWire_ >= 0 && type_ != Wire::SequenceEnd &&
    static_cast<long>(fieldId) >= elemBound_)
{
    if (static_cast<int>(type_) != elemWire_) { skipElem = true; ++skipped_; }
    ...
```

An in-range mistyped element is skipped by some other path (the control proves it is skipped),
but `elemBound_` evidently stays armed for the ids read while that skip is in progress. The fix
is to suspend the wrapper's element-index bound for the duration of a skipped subtree — the
child ids inside it are not element indices.

*Caveat:* the line above is where the bound is consulted, not a confirmed root cause. The
behavioural evidence is solid; the exact code path is for the maintainer to confirm.
